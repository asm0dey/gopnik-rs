# String pointers recovered from code immediates (Task 4b)

Source: `data/string_pointers.json`, generated by `tools/ghidra/DumpImmediates.java`
via `tools/ghidra/run_ghidra.sh`, run against the Ghidra project created by
Task 4 (`ghidra_proj/`, gitignored, import of `orig/g.exe`). The full,
per-candidate audit trail (one row per operand examined, with its
instruction address, mnemonic, operand index, immediate, computed file
offset, full instruction text, disposition — `KEEP`, `reject:not-a-string`,
`reject:out-of-bounds`, or `reject:interior:<covering-offset>` — and an
acceptance-reason column recording the mnemonic and operand kind that
produced the hit) is committed at `data/string_pointers_audit.tsv`
(regenerate with `./tools/ghidra/run_ghidra.sh`; a working copy is also
written to the gitignored `build/`).

## Why this exists

Task 2's length-prefix byte scan is structurally ambiguous: an ASCII space
(`0x20`) is indistinguishable from a Pascal shortstring length byte of 32, so
the scanner can resynchronise mid-string and emit truncated fragments (e.g.
offset `0xBCF8` yielded `'боксёров(-75% что сломают челюст'`, missing the
closing `ь)`). This task instead recovers the true string starts from the
16-bit operands that the compiled code actually uses as string addresses —
evidence, not a byte-pattern guess.

## Revision history (this document)

This is the fourth revision.

**Revision 4 (round-2 review fix)** replaces the operand-extraction method
entirely and adds an interior-offset check, in response to two Critical
findings:

1. **Operand-type contamination.** Revision 3 walked
   `Instruction.getOpObjects(opIndex)` and treated every `Scalar` object
   found inside an operand as a candidate, including scalars that are part
   of a memory-addressing *expression* rather than a bare immediate — e.g.
   the displacement `4` inside `LDS SI,[BP + 0x4]`, or the address inside
   `CMP word ptr [0x38C5], 0x0`. This produced two confirmed classes of
   false positive: the `0x18D0`–`0x18DA` run (small stack-frame
   displacements 0, 2, 4, 6… colliding with the image base) and `0x5195`
   (accepted only via `CMP`/`ADD`/`INC` on an unrelated global counter at
   `word ptr [0x38C5]`; `0x5195` is actually byte 8 of the real string at
   `0x518D`). This revision uses `Instruction.getScalar(opIndex)` instead,
   which returns non-null only when an operand decomposes to exactly one
   object and that object is a bare `Scalar` — i.e. the operand *is* an
   immediate, not an addressing expression built from a register plus a
   displacement. This is applied across all mnemonics, exactly as before;
   the breadth requirement was always about not restricting to `MOV`/`PUSH`,
   never about accepting address arithmetic.
2. **Interior-offset collisions.** Even with `getScalar`, two independent
   genuine immediate operands can coincidentally target the same constant
   pool region: one at a string's real start, another a few bytes into that
   string's own payload where a content byte happens to look like a valid
   length prefix (the same space-misread-as-length-byte pathology, arriving
   through a different door). This revision rejects any content-filter-passing
   candidate that falls strictly inside an already-*confirmed* candidate's
   payload span. The confirmation set matters: a candidate must not be
   allowed to use a misframed, not-yet-rejected candidate as its own
   "container" (that produced a transitive false rejection in an
   intermediate version of this fix, incorrectly discarding two genuine
   strings, `0x5075` and `0x5569`, because each sat immediately after a real
   string whose payload coincidentally contained a byte that also looked
   like a valid length-prefixed start). The final algorithm processes
   candidates in ascending offset order and checks each only against
   candidates already confirmed real, which is sound because a container's
   offset is always numerically smaller than any offset interior to it.
3. Revision 3 also stated the binary "contains no `LES`/`LDS` instructions at
   all — 0 occurrences among the 19480". That claim was false: the same
   revision's own committed `data/string_pointers_audit.tsv` contained 70
   rows with mnemonic `LES`/`LDS` (lines 309, 1670, 1673, among others) —
   they simply never survived to `KEEP`. This revision corrects the claim:
   the disassembly contains **71 `LES`/`LDS` instructions** (counted
   directly from the mnemonic during the Ghidra pass, not from audit-row
   presence). Under `getScalar`, none of them produce a hit at all, because
   every `LES`/`LDS` operand seen in this binary is a memory expression
   (base register plus displacement or a bracketed direct address), which
   `getScalar` correctly declines to decompose. See "LES/LDS, corrected"
   below.

The third revision (Task 4c) changed the coverage assertion's residual bound
from `<= 10` to `<= 14` and excluded offsets landing on a slot of the two
indexed string-array tables (`tools/extract_tables_indexed.py`) — that part
is unchanged by this revision; see "Coverage, both directions" below for the
re-measured counts under the new extraction method.

The first revision made two mistakes, both corrected in the second revision:
restricting extraction to `MOV`/`PUSH` only, and a reuse-count filter that
wrongly discarded real game text (`0xA71D` `'Не хватает'`, `0xB00C`
`'Продать вещи'`). Both remain fixed in this revision — no mnemonic
restriction and no reuse/reference-count filter is applied anywhere in the
current extraction; see "Confirmed still present" below.

## Address mapping

The program image begins at file offset `0x18D0` and loads at segment
`0x1000` (verified in Task 4: `CODE_0` is `1000:0000`, 61008 bytes).
Ghidra's memory blocks for this import (`CODE_0`..`CODE_5`, `DATA`, `HEADER`)
are all part of one contiguous flat image. So for an instruction at segment
`S`, a 16-bit value `imm` used as a near offset within that instruction's own
segment maps to:

```
file_offset = 0x18D0 + (S - 0x1000) * 16 + imm
```

For `S == 0x1000` (`CODE_0`, where the vast majority of instructions live)
this is `file_offset = 0x18D0 + imm`. Verified example: instruction
`1000:e558` is `MOV DI, 0xA40D`, giving `file_offset = 0x18D0 + 0xA40D =
0xBCDD`. `blob[0xBCDD]` is `0x3D` (length 61, corrected from an earlier
misread of `0x3E`/62 in an older revision of this document), and the
following 61 bytes CP866-decode to the complete string
`'30^7  купить зубную защиту боксёров(-75% что сломают челюсть)'` —
correctly terminated, the case that was truncated under Task 2's blind scan.

## Extraction method

`DumpImmediates.java` iterates `currentProgram.getListing().getInstructions(true)`
(19480 instructions, matching Task 4's verified count) and, for **every**
instruction regardless of mnemonic, for each operand:

1. Calls `Instruction.getScalar(opIndex)`. This is non-null only when the
   operand is a bare immediate — i.e. its object list has exactly one
   element and that element is a `Scalar`. Operands that are memory
   expressions (`[BP + 0x4]`, `word ptr [0x38C5]`) or branch targets Ghidra
   has resolved to an `Address` return `null` here and are skipped
   entirely — no displacement, index, or address-expression component is
   ever treated as a candidate.
2. Keeps 16-bit scalars (`0x0000`–`0xFFFF`) and computes `file_offset` per
   the mapping above, discarding anything outside `[0, len(orig/g.exe))`
   (`reject:out-of-bounds`).
3. Applies the content filter (below) to the remaining candidates
   (`reject:not-a-string` on failure).
4. Rejects any content-filter-passing candidate that falls strictly inside
   an already-confirmed candidate's payload span (`reject:interior:<offset>`,
   naming the covering offset).

**2964** (instruction, operand) scalar hits were examined; **758** distinct
file offsets passed the content filter; **63** of those were then rejected
as interior to another; **695** file offsets were accepted overall. Every
row in `data/string_pointers_audit.tsv` also carries a `reason` column
(`<mnemonic>/immediate-scalar`) recording why the hit was produced, so a
future regression to non-immediate operand handling would show up as rows
whose reason does not end in `/immediate-scalar`, or — more directly — as
the reappearance of `LES`/`LDS` rows or of small-displacement collisions in
the `0x18D0`+ region.

No mnemonic restriction and no reuse/reference-count filter is applied
anywhere in this pipeline.

## Content filter (genuine string starts)

Unchanged from earlier revisions. A candidate offset qualifies when
`blob[off]` is a length `N` in `3..=250`, `off + 1 + N <= len(blob)`, and
every payload byte is printable ASCII (`0x20..0x7E`), CP866 high-range
(`0x80..0xF1`), or one of the separators `0x07`, `0x0A`, `0x0D` (`0x07` is
the original's legitimate in-string line-break marker for multi-line menus,
not noise).

## LES/LDS, corrected

The disassembly contains **71 `LES`/`LDS` instructions** (counted directly
by mnemonic during the Ghidra pass; see `LES/LDS-instructions=71` in the
script's own log output and reproducible via
`awk -F'\t' '$2=="LES"||$2=="LDS"' data/string_pointers_audit.tsv` against
the *previous* (pre-fix) audit trail, which recorded 70 rows for them before
`getScalar` was adopted — the earlier claim that they don't occur in this
binary at all was false). Under `getScalar`, they now produce **zero** audit
rows: every `LES`/`LDS` operand in this binary's disassembly is a bracketed
memory expression (e.g. `[BP + 0x4]`), which decomposes to more than one
op-object and so `getScalar` correctly returns `null` for it. This is the
expected, correct behaviour under the new rule, not a gap: a far-pointer
load's *effective address* is not a static immediate operand of the `LES`/
`LDS` instruction itself, so there is nothing for a per-instruction operand
scan to recover here regardless of extraction method.

## Result

**695 string pointers** recovered (`data/string_pointers.json`), all
sorted, deduplicated, well-formed per the content filter, with `0xBCDD`
present and complete. `0xA71D` (`'^4Не хватает'`) and `0xB00C`
(`'^0Продать вещи\'`) are both present, reached by genuine `MOV DI, <imm>`
instructions at multiple call sites each — confirming the reuse-filter
regression from revision 1 remains fixed (frequency plays no role in
acceptance).

`0x5195` is **absent** — it now produces no audit row at all (not even a
rejected one), because the only operand that used to reach it,
`word ptr [0x38C5]` in `CMP`/`ADD`/`INC` instructions, is a memory
expression and `getScalar` never returns a scalar for it.

## The `0x18D0`–`0x18DA` region, precisely

The consecutive **run** is gone: offsets `0x18D1`–`0x18DA` are absent from
`data/string_pointers.json`. Their previous cause (revision 3) was
`getOpObjects` decomposing memory-expression displacements — e.g.
`LDS SI,[BP + 0x4]` yielding `0x18D0 + 4 = 0x18D4`. Under `getScalar`, no
such displacement is ever extracted; the audit trail confirms the rows that
used to land on `0x18D2`, `0x18D4`, etc. are now `reject:interior:0x18D0`
instead — their (imm, file_offset) pairs are *still produced*, but now via
completely unrelated **genuine bare immediates** that happen to numerically
equal a small offset from the image base (e.g. `MOV AX,0x4`, `SUB SP,0x4`,
`RET 0x2` — ordinary function-prologue and stack-cleanup constants), and
they are now correctly rejected because they fall inside `0x18D0`'s own
accepted 64-byte payload span, not because of any special-case filter.

**`0x18D0` itself is still present** — this was not verified false by either
review finding, and it is not eliminated by this revision's fix, because it
is not a decomposed memory-expression artefact in the first place. Every one
of the 357 audit rows landing on it (checked exhaustively — `awk -F'\t'
'$5=="0x18D0" && $7=="KEEP"' data/string_pointers_audit.tsv | wc -l`) comes
from a genuine bare immediate `0x0` in an ordinary `CMP reg/mem, 0` or
`MOV reg, 0` instruction — the single most common immediate value in any
x86 binary — which trivially maps to the image base under
`file_offset = 0x18D0 + imm`. None of them are `MOV DI, <addr>`-style
string-pointer loads. This is disclosed, not hidden, and it is **not**
special-cased away: doing so would mean filtering by mnemonic or by the
specific value `0x0`/offset `0x18D0`, which the brief and the task
constraints both forbid. It is a residual, structurally-inherent false
positive of a value-collision kind that per-instruction operand scanning
cannot distinguish from a real reference without additional signal (e.g.
data-flow tracing into the RTL string-print call), which is out of scope
here. Its content (`'                  ^0┌──── ┌────┐ ┌────┐  │    │  │  ...'`,
box-drawing characters at the very start of the code segment) is at least
plausible as genuine embedded UI-banner data rather than pure garbage, but
that is not verified and is not required either way — the point is that the
false-positive-risk is disclosed, not asserted as a fact in either
direction.

## Coverage, both directions

Cross-checked against Task 2's old blind scan (`data/strings.json`, 696
entries, 657 non-suspect):

- **Forward (new → old): 562 of the 695 new offsets match an old-scan
  offset** (558 match a non-suspect one). The remaining ~133 are new starts
  the old scan never proposed.
- **Reverse (old → new): 68 of the 657 non-suspect old-scan entries are
  initially unaccounted for** — neither present as a new pointer nor inside
  any new pointer's payload span. Of those, **54** land exactly on a
  `base + i*256` slot of one of Task 4c's two indexed string-array tables
  (`0x123DE` / `0x12EF2`, stride 256) and are excluded from the coverage
  assertion for the reason given in Task 4c: no literal pointer to those
  elements exists anywhere in the binary, so pointer recovery structurally
  cannot find them regardless of extraction method. (These re-measured
  counts, 68 and 54, differ slightly from the previous revision's 67 and 53
  — the interior-rejection algorithm change shifted which offsets land
  inside an accepted span by one — but the residual is identical.)
- **The remaining 14** do not land on either table's stride and are
  diagnosed individually below. This is the same set of 14 offsets as the
  previous revision, independently re-derived from the current audit trail
  rather than carried forward.

`tools/test_string_pointers.py` asserts the residual count is `<= 14`.

## Rejected candidates (summary)

Full per-candidate detail is in `data/string_pointers_audit.tsv`. Rejection
reasons:

- `reject:out-of-bounds` (35 rows) — the computed file offset falls outside
  `[0, len(orig/g.exe))`.
- `reject:not-a-string` (808 rows) — the byte at the candidate offset is not
  a plausible shortstring length prefix, or the payload it implies contains
  a disallowed byte, or the payload would run past end-of-file.
- `reject:interior:<offset>` (984 rows, 63 distinct offsets) — the candidate
  falls strictly inside an already-confirmed candidate's payload span.

No candidate is ever rejected for being referenced by "too many"
instructions, and no candidate is ever rejected or accepted based on its
mnemonic; both filters were removed in earlier revisions and neither has
been reintroduced.
