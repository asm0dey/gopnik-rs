# String pointers recovered from code immediates (Task 4b)

Source: `data/string_pointers.json`, generated by `tools/ghidra/DumpImmediates.java`
via `tools/ghidra/run_ghidra.sh`, run against the Ghidra project created by
Task 4 (`ghidra_proj/`, gitignored, import of `orig/g.exe`). Audit trail
(one row per candidate scalar operand examined, with its address, mnemonic,
immediate, computed file offset, full instruction text, and disposition) is
written to `build/string_pointers_audit.tsv` (gitignored; regenerate with
`./tools/ghidra/run_ghidra.sh`).

## Why this exists

Task 2's length-prefix byte scan is structurally ambiguous: an ASCII space
(`0x20`) is indistinguishable from a Pascal shortstring length byte of 32, so
the scanner can resynchronise mid-string and emit truncated fragments (e.g.
offset `0xBCF8` yielded `'боксёров(-75% что сломают челюст'`, missing the
closing `ь)`). This task instead recovers the true string starts from the
16-bit immediate operands that the compiled code actually uses as string
addresses — evidence, not a byte-pattern guess.

## Address mapping

The program image begins at file offset `0x18D0` and loads at segment
`0x1000` (verified in Task 4: `CODE_0` is `1000:0000`, 61008 bytes).
Ghidra's memory blocks for this import (`CODE_0`..`CODE_5`, `DATA`, `HEADER`)
are all part of one contiguous flat image — e.g. `CODE_0` is 0xEE50 bytes
long and the next block starts at segment `1ee5`, i.e. exactly
`0x1000 + 0xEE50/16`, confirming the blocks are laid out back-to-back with no
gaps. So for an instruction at segment `S`, offset `O` (a
`ghidra.program.model.address.SegmentedAddress`), a 16-bit scalar operand
`imm` used as a near offset within that instruction's own segment maps to:

```
file_offset = 0x18D0 + (S - 0x1000) * 16 + imm
```

For `S == 0x1000` (`CODE_0`, where the vast majority of instructions live)
this is exactly `file_offset = 0x18D0 + imm`, matching the brief's rule and
the verified example: instruction `1000:e558` is `MOV DI, 0xA40D`, giving
`file_offset = 0x18D0 + 0xA40D = 0xBCDD`, which decodes to the complete
string `'30^7  купить зубную защиту боксёров(-75% что сломают челюсть)'`
(length byte `0x3E` = 62, CP866-decoded, correctly terminated — the case
that was truncated under the old scan). For instructions in other blocks
(e.g. segment `1f16`, `1f78`), the base is derived from that instruction's
own segment per this formula rather than assuming `0x1000`, per the brief's
instruction not to hard-code the CODE_0 base.

## Extraction method

`DumpImmediates.java` iterates `currentProgram.getListing().getInstructions(true)`
(19480 instructions, matching Task 4's verified count) and, for each
instruction:

1. Restricts to `MOV` and `PUSH` mnemonics — the instruction classes Borland
   Pascal's codegen uses to load a register (or push a value) with the
   *address* of a string constant, as opposed to `CMP`/`ADD`/`SUB`/`SHL`/
   `RET`/etc., which use immediates for arithmetic, comparison, or stack
   cleanup and never carry a pointer value.
2. For each operand, calls `instr.getScalar(opIndex)` — this reads the
   **actual decoded immediate Ghidra attached to a real, byte-accurate
   disassembled instruction**, not a byte-pattern match. This is the
   required difference from a naive scan for opcodes `BA`/`B8`/`BF`/`BE`/`68`:
   that approach was tried first and produced 218 false starts, including a
   consecutive run at `0x18D0`-`0x18DA` — the signature of random byte pairs
   inside real instructions being misread as fake opcodes with fake operands.
3. Keeps only scalars with `bitLength() == 16` (a true 16-bit immediate
   field, matching how MOV/PUSH imm16 always encode regardless of the
   value's magnitude) and unsigned value in `0x0000..0xFFFF`.
4. Computes `file_offset` per the mapping above and discards anything
   outside `[0, len(orig/g.exe))` (11 instances rejected this way, all from
   RTL code blocks `1f16`/`1f78` referencing far-out-of-range immediates
   like `0xD7B0`/`0xFFFF` that are evidently not this image's own pointers).

1906 (instruction, operand) hits passed steps 1-3 above and were in bounds;
742 distinct file offsets remained after deduplication.

## Content filter (genuine string starts)

A candidate offset qualifies when `blob[off]` is a length `N` in `3..=250`,
`off + 1 + N <= len(blob)`, and every payload byte is printable ASCII
(`0x20..0x7E`), CP866 high-range (`0x80..0xF1`), or one of the separators
`0x07`, `0x0A`, `0x0D` (`0x07` is the original's legitimate in-string
line-break marker for multi-line menus, not noise). This rejected 566 of
the 1906 examined hits (candidates landing on bytes that are not a
well-formed shortstring at all).

## Reuse-count filter

Applying only the two filters above still left a visible defect: a
consecutive run of accepted offsets at `0x18D0`-`0x18DA` — the exact
signature the brief warns is characteristic of noise, this time arising for
a *different* reason than the byte-scan's false opcodes. Manual inspection
of the audit trail showed the true cause: this file region holds one long,
mostly-whitespace/box-drawing-character ASCII-art string, which (like any
long run of spaces) is internally ambiguous under the length-prefix rule —
many nearby starting offsets validate. Separately, small immediate values
(`0`-`10`) are the single most common operand value in *any* compiled
program (loop counters, comparisons repurposed here as `MOV`/`PUSH`
operands too), so hundreds of semantically unrelated instructions scattered
across the whole binary numerically collided with this one narrow, already
ambiguous byte range purely because `0x18D0 + small_number` lands inside it.

The evidence-based fix: a genuine string-literal reference is emitted once
per occurrence of the literal in the Pascal source, so a real pointer is
loaded by a small, bounded number of distinct instruction addresses.
Offsets referenced by an implausibly large number of distinct instructions
are not unique literal addresses — manual inspection of every offset with
5+ references showed each one is the exact same `MOV DI, imm16` instruction
recurring verbatim across many unrelated functions (e.g. `MOV DI,0x379C`
at 17 different addresses, `MOV DI,0x973C` at 6), the signature of a
compiler-emitted shared workspace-buffer or record-field-offset constant,
not a per-literal address.

`DumpImmediates.java` therefore keeps only offsets referenced by at most 4
distinct instructions (`REUSE_LIMIT = 4`). This threshold was set by manual
inspection, not by tuning it against the test:
- At reference count 4, there are exactly two candidate offsets. One,
  `0x1AD0`, decodes to `'...Версия 1.0'` ("Version 1.0") — unambiguously
  genuine text, plausibly shown from a handful of screens — so it is kept.
  (The other, `0x18D6`, is inside the ambiguous box-drawing cluster above;
  it is retained too since the rule is offset-based, but it does not by
  itself break the "no consecutive false-start run" property below.)
- At reference count 5 and above (24 unique offsets total, all in
  `docs/re/string-pointers.md`-adjacent regions like `0x18D0`-`0x19CF`,
  `0x506C`, `0x5554`, `0xA71D`, `0xB00C`), every offset inspected decodes to
  either the same box-drawing/filler region or a `MOV DI,<const>` repeated
  boilerplate pattern — no further genuine text was found — so the limit
  stops at 4.

This rejected 537 (instruction, offset) hits, spanning 24 distinct offsets:
`0x18D0`-`0x18D5`, `0x18D7`, `0x18D8`, `0x18DA`, `0x18DF`, `0x18E2`,
`0x18E4`, `0x1900`-`0x1902`, `0x1904`, `0x1934`, `0x1953`, `0x19CF`,
`0x1DF1`, `0x506C`, `0x5554`, `0xA71D`, `0xB00C`.

After this filter, the `0x18D0`-`0x18DA` window contains only `0x18D6`
(count 4) and `0x18D9` (count 1, single reference, passes independently) —
2 offsets, at the brief's stated limit. Both are individually well-formed
per the content filter and have low reference counts; they are kept as
genuinely uncertain rather than force-excluded, and are called out here as
the known residual ambiguity in this region rather than presented as
confirmed strings.

## Result

**718 string pointers** recovered and validated (`tools/test_string_pointers.py`
passes: sortedness, uniqueness, `>=400` count, well-formed length-prefix at
every offset, `0xBCDD` present and complete, and the `0x18D0`-`0x18DA` run
at ≤2). Cross-checked against Task 2's old scan (`data/strings.json`, 696
entries, 657 non-suspect): 560 of the 718 new offsets agree with an old-scan
offset overall (556 with a non-suspect one), close to the brief's stated
558, and 158 are newly recovered starts the old scan never proposed — likely
including some of the 60-90 strings the brief describes as misframed by the
old scan's ambiguous resync.

## Rejected candidates and why (summary)

- **11 hits, out of file bounds**: instructions in RTL code blocks `1f16`
  and `1f78` (e.g. `MOV AX,0xD7B0`, `MOV AX,0xFFFF`) whose computed file
  offset exceeds `len(orig/g.exe)` — clearly not this image's own string
  pointers (likely RTL-internal segment/handle constants unrelated to
  string addressing).
- **566 hits, not a well-formed shortstring**: the candidate offset's byte
  is not a plausible length prefix, or the resulting payload contains a
  byte outside the allowed CP866/ASCII/separator set.
- **537 hits (24 distinct offsets), reused shared-constant**: see the
  reuse-count filter section above — a small number of file offsets
  attract dozens to nearly 100 distinct, otherwise-unrelated instructions
  either because they fall inside a single ambiguous whitespace/box-drawing
  string, or because the literal `MOV DI,<value>` sequence is a reused
  compiler-emitted buffer/field-offset constant, not a unique string
  address. Full list: `0x18D0-0x18D5, 0x18D7, 0x18D8, 0x18DA, 0x18DF,
  0x18E2, 0x18E4, 0x1900-0x1902, 0x1904, 0x1934, 0x1953, 0x19CF, 0x1DF1,
  0x506C, 0x5554, 0xA71D, 0xB00C`.

Per this project's "unknown means unknown" rule, none of the above are
asserted to be real strings that were incorrectly dropped — they are
recorded as excluded and why, not resolved by invented justification.
