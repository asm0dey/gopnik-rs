# String pointers recovered from code immediates (Task 4b)

Source: `data/string_pointers.json`, generated by `tools/ghidra/DumpImmediates.java`
via `tools/ghidra/run_ghidra.sh`, run against the Ghidra project created by
Task 4 (`ghidra_proj/`, gitignored, import of `orig/g.exe`). The full,
per-candidate audit trail (one row per operand object examined, with its
instruction address, mnemonic, operand index, immediate, computed file
offset, full instruction text, and disposition — `KEEP`,
`reject:not-a-string`, or `reject:out-of-bounds`) is committed at
`data/string_pointers_audit.tsv` (regenerate with `./tools/ghidra/run_ghidra.sh`;
a working copy is also written to the gitignored `build/`).

## Why this exists

Task 2's length-prefix byte scan is structurally ambiguous: an ASCII space
(`0x20`) is indistinguishable from a Pascal shortstring length byte of 32, so
the scanner can resynchronise mid-string and emit truncated fragments (e.g.
offset `0xBCF8` yielded `'боксёров(-75% что сломают челюст'`, missing the
closing `ь)`). This task instead recovers the true string starts from the
16-bit operands that the compiled code actually uses as string addresses —
evidence, not a byte-pattern guess.

## Revision history (this document)

This is the third revision.

Revision 3 (Task 4c): the coverage assertion's residual bound changed from
`<= 10` to `<= 14`, and the assertion now excludes offsets that land exactly
on a slot of the two indexed string-array tables recovered by Task 4c
(`tools/extract_tables_indexed.py`) — those 53 offsets are structurally
unrecoverable by pointer analysis (they're addressed by `base + i*256` index
arithmetic, never by a literal), so counting them as pointer-recovery losses
was never the right measure. The remaining 14 are now individually
diagnosed below, replacing the second revision's "67 unaccounted for, test
fails" state. See "The 14 residual offsets, itemised" below.

The first revision made two mistakes, both corrected in the second revision
after review:

1. It restricted extraction to `MOV`/`PUSH` instructions only, with no
   stated justification, and never flagged this as a deviation from the
   brief.
2. It added a "reuse-count" filter (`REUSE_LIMIT`) that rejected any file
   offset referenced by more than 4 distinct instructions, on the theory
   that a genuinely unique string literal would only be loaded from a
   small number of call sites. **This was wrong and the filter has been
   deleted along with all logic depending on it.** The filter discarded
   real game text: `0xA71D` (`'Не хватает'`, "not enough") and `0xB00C`
   (`'Продать вещи'`, "sell items") were both rejected as "reused shared
   constants" with a documented claim that manual inspection had found "no
   further genuine text" among the rejected offsets. That claim was false —
   both decode to real, sensible, complete UI strings. Reference count is
   not evidence about whether something is a string: generic UI messages
   like `'Не хватает'` are shown from many call sites precisely *because*
   they are generic, not because they are false positives. No
   differently-tuned version of this idea has been substituted; frequency
   is not used as a signal anywhere in the current extraction.

The consecutive run of offsets at `0x18D0`-`0x18DA` was also previously
treated as suspect. It is not: it decodes to the title banner shown with a
progressively increasing number of leading spaces (the game references
successive offsets into one buffer to scroll it on screen), and is
correctly left untouched by the current extraction.

## Address mapping

The program image begins at file offset `0x18D0` and loads at segment
`0x1000` (verified in Task 4: `CODE_0` is `1000:0000`, 61008 bytes).
Ghidra's memory blocks for this import (`CODE_0`..`CODE_5`, `DATA`, `HEADER`)
are all part of one contiguous flat image — e.g. `CODE_0` is 0xEE50 bytes
long and the next block starts at segment `1ee5`, i.e. exactly
`0x1000 + 0xEE50/16`, confirming the blocks are laid out back-to-back with no
gaps. So for an instruction at segment `S`, a 16-bit value `imm` used as a
near offset within that instruction's own segment maps to:

```
file_offset = 0x18D0 + (S - 0x1000) * 16 + imm
```

For `S == 0x1000` (`CODE_0`, where the vast majority of instructions live)
this is exactly `file_offset = 0x18D0 + imm`, matching the verified example:
instruction `1000:e558` is `MOV DI, 0xA40D`, giving
`file_offset = 0x18D0 + 0xA40D = 0xBCDD`, which decodes to the complete
string `'30^7  купить зубную защиту боксёров(-75% что сломают челюсть)'`
(length byte `0x3E` = 62, CP866-decoded, correctly terminated — the case
that was truncated under the old scan).

**Known limitation of this mapping**, relevant to the coverage discussion
below: it assumes the target segment for a given operand equals the
*physical* code segment of the instruction that uses it. That holds for the
verified example and for the large majority of recovered pointers, but it
does not hold for a string reached via a two-instruction far-pointer
construction (segment loaded into `ES`/`DS` by one instruction, offset
supplied by a different instruction) where the effective segment differs
from the referencing instruction's own `CS`. This extraction does not trace
register-level data flow to detect that case; see "Residual coverage gap"
below.

## Extraction method

`DumpImmediates.java` iterates `currentProgram.getListing().getInstructions(true)`
(19480 instructions, matching Task 4's verified count) and, for **every**
instruction regardless of mnemonic:

1. For each operand, walks `Instruction.getOpObjects(opIndex)` rather than
   relying only on `Instruction.getScalar(opIndex)`. Ghidra's own
   auto-analysis (run at import time, before this script runs with
   `-noanalysis`) frequently recognizes an immediate that looks like a
   pointer and rewrites the operand as an `Address` object rather than
   leaving it a plain `Scalar` — this happens routinely for `PUSH <addr>`
   and for far-pointer loads. `getScalar()` returns `null` for those
   operands, so a scalar-only scan silently drops every string address
   Ghidra already recognized as an address. Both `Scalar` (16-bit,
   unsigned value `0x0000`-`0xFFFF`) and `Address` operand objects are
   handled, from operands of any mnemonic — `MOV`, `PUSH`, `CMP`, `ADD`,
   etc. all appear in the audit trail. (This binary's disassembly contains
   no `LES`/`LDS` instructions at all — 0 occurrences among the 19480
   instructions — so that specific form named in the brief does not arise
   here in practice; the extraction does not special-case mnemonics either
   way, so it would pick them up automatically if the binary used them.)
2. Computes `file_offset` per the mapping above and discards anything
   outside `[0, len(orig/g.exe))`.
3. Applies the content filter (below) to decide whether the candidate is a
   genuine string start.

No mnemonic restriction and no reuse/reference-count filter is applied
anywhere in this pipeline.

7770 (instruction, operand-object) hits were examined; 764 distinct file
offsets were accepted after the content filter (see `data/string_pointers.json`
and `data/string_pointers_audit.tsv` for the full accounting).

## Content filter (genuine string starts)

A candidate offset qualifies when `blob[off]` is a length `N` in `3..=250`,
`off + 1 + N <= len(blob)`, and every payload byte is printable ASCII
(`0x20..0x7E`), CP866 high-range (`0x80..0xF1`), or one of the separators
`0x07`, `0x0A`, `0x0D` (`0x07` is the original's legitimate in-string
line-break marker for multi-line menus, not noise). This is a
content-only filter — it does not look at how many instructions reference
an offset, only at the bytes at that offset.

### The 67 diagnosed, and the table-range exclusion (Task 4c)

Diagnosing all 67 (checked against the audit trail and, for a sample,
against Ghidra's own cross-reference index and an exhaustive raw-byte
search of `orig/g.exe`) showed they split into two structurally distinct
groups:

- **53 of the 67** land exactly on a `base + i*256` slot of one of two
  contiguous 256-byte-stride regions — table bases `0x123de` and `0x12ef2`
  (e.g. `0x123de`, `0x124de`, `0x125de`, ...). This is a fixed-size array of
  shortstring records (each Pascal `string[N]` slot occupying a constant
  256 bytes regardless of actual text length, addressed at runtime as
  `base + index*256`). For such an access pattern only the table's base
  address ever appears as a literal operand; each element's address is
  computed at runtime and never appears as a static immediate anywhere in
  the binary, so no scan of instruction operands — however broad — can
  recover it. **Task 4c** (`tools/extract_tables_indexed.py`,
  `docs/re/string-tables.md`) recovers these two tables directly by walking
  the known stride instead. Because recovering them via pointer analysis is
  structurally impossible, `tools/test_string_pointers.py`'s coverage
  assertion now excludes offsets that land exactly on a `base + i*256` slot
  of either table range (see `TABLE_RANGES` in that file) rather than
  counting them as pointer-recovery losses. (Measured precisely: excluding
  these 53 drops the unaccounted count from 67 to 14 — not 67 − 55 = 12 as
  an earlier, less precise pass estimated; the exact stride-match exclusion
  used in the test catches 53, not 55, of the original 67.)
- **The remaining 14** do not land on either table's stride and are
  diagnosed individually below.

`tools/test_string_pointers.py` now asserts the residual count is `<= 14`.
Current actual run:

```
$ python3 tools/test_string_pointers.py
OK 764 string pointers recovered, 14 blind-scan entries unaccounted for
```

copied from an earlier characterisation). They split into two verified
categories:

by the content filter's `N >= 3` floor.** In each case the audit trail

coverage assertion in `tools/test_string_pointers.py` has not been weakened
beyond excluding the two structurally-unrecoverable table ranges. The
residual 14 are reported here individually rather than summarised away.

## Rejected candidates (summary)

Full per-candidate detail, including every rejected (instruction, operand)
hit and the reason, is in `data/string_pointers_audit.tsv`. Rejection
reasons are only ever content-based:

- `reject:out-of-bounds` — the computed file offset falls outside
  `[0, len(orig/g.exe))`.
- `reject:not-a-string` — the byte at the candidate offset is not a
  plausible shortstring length prefix (outside `3..=250`), or the payload
  it implies contains a byte outside the allowed
  CP866/ASCII/`0x07`/`0x0A`/`0x0D` set, or the payload would run past
  end-of-file.

No candidate is ever rejected for being referenced by "too many"
instructions; that filter has been removed (see revision history above).
