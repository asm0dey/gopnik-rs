# .SAV file format (Task 5)

Source: `data/save_layout.json`, generated by `tools/decode_save.py`
(pure Python, standard library only — no external tooling). Validated
against all five reference saves shipped in `orig/`: `SAVE_R0.SAV`,
`SAVE_R2.SAV`, `SAVE_R3.SAV`, `SAVE_R4.SAV`, `SAVE_R5.SAV`.

## Layout

Every `.SAV` file is exactly 694 bytes.

| offset | kind          | len | name        | status                          |
|--------|---------------|-----|-------------|----------------------------------|
| 0x000  | `pstring`     | 256 | `magic`     | confirmed — constant version banner |
| 0x100  | `pstring`     | 256 | `name`      | confirmed — player name, colour-prefixed |
| 0x200  | `u16`         | 2   | `unk_stat0` | **unknown** — see below |
| 0x202  | `u16`         | 2   | `unk_stat1` | **unknown** |
| 0x204  | `u16`         | 2   | `unk_stat2` | **unknown** |
| 0x206  | `u16`         | 2   | `unk_stat3` | **unknown** |
| 0x208  | `u16`         | 2   | `unk_stat4` | **unknown** |
| 0x20a  | `u16`         | 2   | `unk_stat5` | **unknown** |
| 0x20c  | `u16`         | 2   | `unk_stat6` | **unknown** |
| 0x20e  | `u16`         | 2   | `unk_stat7` | **unknown** |
| 0x210  | `u16`         | 2   | `hp`        | confirmed — current hit points |
| 0x212  | `u16`         | 2   | `hpmax`     | confirmed — maximum hit points |
| 0x214  | `bytes`       | 162 | `tail`      | **unknown**, opaque — flags, counters, and a run of Pascal `string[2]` records, not yet segmented |

`0x214 + 162 = 0x2ba = 694`, so the tail runs to end of file.

`pstring` is a Borland Pascal shortstring: one length byte (`0..255`)
followed by up to 255 payload bytes at a fixed 256-byte slot. Text is
stored in CP866, converted to UTF-8 at extraction time (this document and
`data/save_layout.json` hold UTF-8). Payload bytes past the declared length
are not zeroed by Borland's runtime — they are leftover stack/heap garbage
from a previous write and preserved verbatim by the decoder for a byte-exact
round trip; they carry no semantic value.

`^0`–`^7` sigils embedded in `name` are in-band colour markup for the
game's text renderer, not part of the player's typed name. They are
preserved byte-for-byte here because a save file is exactly the place a
byte-exact round trip is required; they must never be treated as literal
name characters anywhere the string is displayed or compared for UI
purposes.

## Observed values (all five reference saves)

| file | magic | name | hp | hpmax | stats (unk_stat0..7) |
|------|-------|------|----|-------|------------------------|
| `SAVE_R0.SAV` | `^4Gopnik: ^7version 1.02 june,sept 2003` | `^7 adg` | 118 | 129 | `[4, 24, 13, 19, 7, 15, 17, 29]` |
| `SAVE_R2.SAV` | (same) | `^7 vor` | 84 | 99 | `[6, 16, 15, 15, 17, 10, 11, 19]` |
| `SAVE_R3.SAV` | (same) | `^7 vor` | 178 | 178 | `[6, 28, 25, 28, 31, 20, 24, 38]` |
| `SAVE_R4.SAV` | (same) | `^7 vor` | 251 | 270 | `[6, 42, 45, 44, 52, 30, 32, 53]` |
| `SAVE_R5.SAV` | (same) | `^7 Mudila` | 325 | 325 | `[5, 90, 120, 45, 49, 40, 57, 102]` |

`magic` is byte-identical across all five saves:
`^4Gopnik: ^7version 1.02 june,sept 2003` — a constant version banner, not
per-save state.

## Unknown / not yet established

Per project convention, a field whose meaning is not confirmed is named
`unk_<hex_offset>` (here `unk_stat0`..`unk_stat7`, since all eight share
the same 16-byte block at 0x200) and its bytes are preserved rather than
guessed at:

- **The eight stat words at 0x200–0x20f.** Values climb steadily with
  character progression (e.g. `unk_stat1` goes 24 -> 16 -> 28 -> 42 -> 90
  across the five saves) which is consistent with them being attributes
  or skills, but no name or semantic meaning is assigned yet. `unk_stat0`
  is notably small and stable-ish (4, 6, 6, 6, 5) relative to the others,
  which climb much further — possibly a different kind of value (e.g. a
  level or class index) rather than a raw stat, but this is speculation,
  not a finding, and is not encoded in the layout.
- **The 162-byte tail at 0x214–0x2b9.** Carried as opaque `bytes` for an
  exact round trip. It is known to contain a run of Pascal `string[2]`
  records among flags/counters, per the brief, but the run has not been
  segmented into individual fields.

Task 9 pins the stat words and segments the tail against the disassembly;
until then this document and `data/save_layout.json` intentionally leave
them as opaque/unknown rather than presenting a guessed layout as settled.

## Validation

`tools/test_decode_save.py` decodes all five reference saves and asserts,
per save:

1. `magic` matches the constant banner.
2. `name`, `hp`, `hpmax` match the values established by inspection above.
3. `hp <= hpmax`.
4. **Independent offset check.** The bytes for every *named* region
   (`magic`, `name`, the eight stat words, `hp`, `hpmax`) are rebuilt from
   the decoded field values alone — never from the stashed raw blob — and
   compared against the corresponding slice of the original file, using
   offsets hardcoded in the test rather than imported from the decoder
   module. This is what actually proves the claimed offsets are correct;
   the tail and shortstring padding remain explicitly out of scope for
   this check and stay declared opaque.
5. **Round trip.** `encode(decode(blob)) == blob` for the full 694 bytes.
   This proves the decoder does not corrupt any byte it re-emits (named
   fields, opaque tail, and shortstring padding alike). It does *not* by
   itself prove any offset is correct — `encode()` starts from a copy of
   the original blob and only overwrites the slices it names, so a wrong
   offset for e.g. `hp` still round-trips byte-identically because the
   "wrong" bytes get copied through untouched either way. Check 4 above is
   what closes that gap; check 5 stays as a useful regression guard on top
   of it.

This was verified directly: temporarily changing `OFF_HP` in
`decode_save.py` from `OFF_STATE + 0x10` to `OFF_STATE + 0x0e` left the
round trip byte-identical (`encode(rec) == blob` still `True`) while the
independent offset check correctly failed
(`hp bytes at 0x210 don't match decoded field`), confirming check 4 does
real work that check 5 alone cannot.

Run: `python3 tools/test_decode_save.py`
