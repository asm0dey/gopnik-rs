# String extraction, re-anchored on recovered pointers (Task 2b)

Source: `data/strings.json`, generated by `tools/extract_strings.py`, which
now reads two evidence-based inputs instead of guessing string boundaries:

- `data/string_pointers.json` (Task 4b) — 695 offsets recovered from real
  16-bit immediate operands in the disassembly.
- `data/string_tables.json` (Task 4c) — 54 entries across the two indexed
  `array[..] of string[255]` tables (`ranks`, `krutizna`), reached only by
  `base + i*256` index arithmetic and invisible to pointer recovery.

## Why this replaces Task 2's output

Task 2's extractor (`scan_blind`, now deleted) walked every byte of
`orig/g.exe` and treated any byte in `3..200` as a plausible Pascal
shortstring length prefix. This is structurally ambiguous: an ordinary
content byte — e.g. an ASCII space, `0x20` — is indistinguishable from a
length prefix of 32. When the scanner resynchronised on such a byte inside
a real string's payload, it split that string into an invented fragment
starting mid-sentence, and left a *truncated* fragment ending mid-sentence
at the point where the byte was misread. This is exactly what happened to
the боксёров line: `orig/g.exe` offset `0xBCDD` holds the complete string
`'30^7  купить зубную защиту боксёров(-75% что сломают челюсть)'`, but the
blind scan started reading at `0xBCDD` correctly, hit the payload's own
space byte at `0xBCF8`, misread it as length 32, and emitted a *second*,
spurious "string" starting there — `'боксёров(-75% что сломают челюст'` —
while (depending on iteration order) the original entry never got to
consume its own tail. No length/Cyrillic-count threshold fixes an ambiguity
like this; the fix is to stop guessing where strings start and anchor on
places the compiled code actually references as string addresses.

`tools/extract_strings.py` no longer contains a blind scanner at all. The
old scan is not retained as `scan_blind()` because the pointer list plus the
table merge fully supersede it: every non-suspect entry the blind scan found
is now either reproduced exactly, subsumed inside a correctly-framed longer
string, or is one of the 14 offsets already itemised and explained in
`docs/re/string-pointers.md` ("The 14 residual offsets, itemised") as
offsets no pointer or table slot reaches. Keeping a second, unused
extraction path around as dead code was judged worse than deleting it.

## Dropped entries: 80 of Task 2's 696, all accounted for

`80` offsets from Task 2's blind scan do not appear in the new list.

**35 were already flagged `suspect` in Task 2.** Spot-checking their `plain`
text confirms these are unstructured byte noise, not text: `X9ыUЛ>`,
`бж8`, `к8бЮ8Щ`, `А<Г>А<`, `2ф6Л`, etc. — no Cyrillic run of 3+, no space,
the same pattern repeated four to six times each (`к8бЮ8Щ` appears at five
different offsets, `бо8гм8` at five more), consistent with the blind
scanner resynchronising on the same repeating machine-code byte pattern at
different points in the binary. None of these offsets are referenced by any
instruction operand in the Ghidra disassembly (Task 4b's audit trail) and
none fall on a table slot, so their disappearance is a correction, not a
loss.

**45 were not flagged `suspect` in Task 2** — real-looking text that

## New entries: 133

133 offsets appear in the new list that were absent from Task 2's. They
fall into four groups:

1. **The splash-screen box-art lines** (`0x18D0` through `0x1FA8`, 18
   entries) — ASCII box-drawing art plus the version banner
   (`'Версия 1.02'` at `0x1AD0`) and `'Нажми какую-нибудь кнопку'` at
   `0x1B0E`. These never satisfied Task 2's `MIN_CYRILLIC = 2` filter on
   their own (most are pure box-drawing characters) or were skipped because
   an earlier misframed candidate consumed the scanner's position; they are
   reachable by real `MOV DI, <imm>` instructions in an evenly-spaced
   sequence (documented in `docs/re/string-pointers.md`, "The `0x18D0`–
   `0x18DA` region, precisely").
2. **Short ASCII command keywords with zero Cyrillic letters**: `run`,
   `kos`, `mar`, `bmar`, `wes`, `rep`, `girl`, `trn`, `name`, `version`,
   `help`, `exit`, `fight`, and save-file name fragments (`save_r`,
   `save_r0.sav`, `.sav`, `places.sav`). Task 2's blind scan required
   `MIN_CYRILLIC = 2` matches, so pure-ASCII command tokens like these could
   never pass regardless of where the scan started. They are real string
   literals the game's text-command parser uses — cross-checked against the
   `'Напиши: <cmd> чтобы ...'` help text also newly recovered (e.g. `mar` /
   `'Напиши: mar  чтобы идти на рынок'`, `rep` / `'...к ветеринару'`, `trn`
   / `'...в качалку'`) — the keyword and its own help line are two separate
   string literals, both now recovered, both referencing each other's
   content.
3. **The re-anchored halves of the 31 misframed strings above** — the
   *correct* start offset (e.g. `0x717B`, `0xC032`, `0xBCDD` itself under
   its now-complete text) is new, replacing the incorrect fragment offset
   Task 2 had instead.
4. **A handful of short/edge fragments now flagged `suspect: True`**, e.g.
   `0x2F2F` `'7777'`, `0x92C4` `'-'`, and four short high-bit noise strings
   at `0x107AE`/`0x10A4B`/`0x11067`/`0x1106C` — these are genuine pointer
   targets (some instruction really does load their address) but their
   content doesn't look like game text, so `is_suspect()` correctly flags
   them. Kept, not deleted, per the standing rule.

## Residual mid-word-cut check: 39 survivors (over the brief's bound of 5)

The brief's check flags any non-suspect entry whose payload's last byte and
the byte immediately following the payload are *both* "alphanumeric"
(CP866 Cyrillic range, ASCII digit, or ASCII letter). Running it against
the new 749-entry list produces **39 survivors**, not the ≤5 the brief
expects. This was investigated rather than tuned away, per the task's
explicit instruction not to weaken the assertion.

**Root cause: every one of the 39 is a correctly-terminated, complete
string. None is actually cut mid-word.** The check's premise — that a real
cut leaves two word-characters glued together across the cut point — holds
for a scan with gaps between accepted spans, but Pascal shortstrings in this
binary's constant pool are packed **back-to-back with no delimiter byte**.
The byte immediately after a complete, correctly-terminated string's payload
is therefore *always* either the length-prefix byte of the very next string,
or (at the end of a string run) the first opcode byte of the following
function's machine code — and both of those bytes have no reason to avoid
the "alphanumeric" ranges the check tests:

- **34 of the 39**: the byte right after the payload is the length prefix
  of another accepted string (`end` offset is itself a key in
  `data/strings.json`). Typical Cyrillic game-text strings run roughly
  10–90 bytes long, and that range overwhelmingly overlaps the check's
  "alphanumeric" byte values (`0x30–0x39`, `0x41–0x5A`, `0x61–0x7A`,
  `0x80–0xAF`, `0xE0–0xF1`) purely by decimal coincidence — a length of 53
  is the ASCII digit-range byte `0x35`('5'), a length of 85 is `0x55`('U'),
  and so on. There is no missing byte in any of these 34 cases; the next
  string simply starts immediately.
- **5 of the 39** (`0x1FE5`, `0x4283`, `0x55B9`, `0x77D2`, `0x8DDC`): the
  byte right after the payload is `0x55` (`PUSH BP`) — the first byte of a
  standard Borland Pascal procedure prologue (`55 89 E5` = `PUSH BP; MOV
  BP,SP`), immediately following the last string in that constant-pool run
  before code resumes. `0x55` happens to equal ASCII `'U'`, which the check
  counts as alphanumeric, but it is machine code, not a text byte.

`data/string_pointers.json` against `data/strings.json` as "the blind scan
to check regressions against." Now that this task has overwritten

of this task's scope to change. The comparison it was written to do (new
pointers vs. Task 2's blind scan) is preserved verbatim in this document's
"Dropped entries" section above, using the blind-scan snapshot from before
this task's commit.
