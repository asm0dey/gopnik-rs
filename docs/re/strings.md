# String extraction, re-anchored on recovered pointers (Task 2b)

Source: `data/strings.json`, generated by `tools/extract_strings.py`, which
now reads two evidence-based inputs instead of guessing string boundaries:

- `data/string_pointers.json` (Task 4b) — 695 offsets recovered from real
  16-bit immediate operands in the disassembly.
- `data/string_tables.json` (Task 4c) — 54 entries across the two indexed
  `array[..] of string[255]` tables (`ranks`, `krutizna`), reached only by
  `base + i*256` index arithmetic and invisible to pointer recovery.

## Why this replaces Task 2's output

Task 2's extractor (`scan_blind`, now deleted) walked every byte of
`orig/g.exe` and treated any byte in `3..200` as a plausible Pascal
shortstring length prefix. This is structurally ambiguous: an ordinary
content byte — e.g. an ASCII space, `0x20` — is indistinguishable from a
length prefix of 32. When the scanner resynchronised on such a byte inside
a real string's payload, it split that string into an invented fragment
starting mid-sentence, and left a *truncated* fragment ending mid-sentence
at the point where the byte was misread. This is exactly what happened to
the боксёров line: `orig/g.exe` offset `0xBCDD` holds the complete string
`'30^7  купить зубную защиту боксёров(-75% что сломают челюсть)'`, but the
blind scan started reading at `0xBCDD` correctly, hit the payload's own
space byte at `0xBCF8`, misread it as length 32, and emitted a *second*,
spurious "string" starting there — `'боксёров(-75% что сломают челюст'` —
while (depending on iteration order) the original entry never got to
consume its own tail. No length/Cyrillic-count threshold fixes an ambiguity
like this; the fix is to stop guessing where strings start and anchor on
places the compiled code actually references as string addresses.

`tools/extract_strings.py` no longer contains a blind scanner at all. The
old scan is not retained as `scan_blind()` because the pointer list plus the
table merge fully supersede it: every non-suspect entry the blind scan found
is now either reproduced exactly, subsumed inside a correctly-framed longer
string, or is one of the 14 offsets already itemised and explained in
`docs/re/string-pointers.md` ("The 14 residual offsets, itemised") as
offsets no pointer or table slot reaches. Keeping a second, unused
extraction path around as dead code was judged worse than deleting it.

   / `'...в качалку'`) — the keyword and its own help line are two separate
   string literals, both now recovered, both referencing each other's

3. **The re-anchored halves of the 31 misframed strings above** — the
   *correct* start offset (e.g. `0x717B`, `0xC032`, `0xBCDD` itself under
   its now-complete text) is new, replacing the incorrect fragment offset
   Task 2 had instead.
4. **A handful of short/edge fragments now flagged `suspect: True`**, e.g.
   `0x2F2F` `'7777'`, `0x92C4` `'-'`, and four short high-bit noise strings

   targets (some instruction really does load their address) but their
   content doesn't look like game text, so `is_suspect()` correctly flags
   them. Kept, not deleted, per the standing rule.

## Structural tiling check (supersedes the next-byte heuristic)

The original mid-word-cut check flagged an entry when its payload's last
byte and the byte immediately following it were both "alphanumeric." That
check is structurally broken and was abandoned, not tuned: strings in this
binary's constant pool are packed **back-to-back with no delimiter byte**,
so the byte after any correctly-terminated string is always either the
length-prefix byte of the very next string or an opcode byte of the
following function's machine code, and both land inside the
"alphanumeric" ranges by ordinary coincidence (a length of 53 is the ASCII
digit `0x35`('5'), `PUSH BP` is `0x55`('U'), etc.). It flagged 34/39 false
positives from adjacent length bytes and 5/39 from `PUSH BP` prologues
alone. A tighter same-alphabet-class variant (matching the length byte's
value against the *specific* character class it collided with, rather than
"alphanumeric" broadly) was also tried and still produced 3 false
positives (`0x1AD0`, `0x7CE3`, `0xBE63`, each followed by a length byte of
`0x35`/`0x37`/`0x31`). No rule that inspects only the single byte after a
string's payload can distinguish "string ends here" from "length byte of
the next string happens to look like a letter." This is itself a real
finding about the binary's layout, not just a test bug, so it is recorded
here per the plan's evidence-in-`docs/re/` requirement rather than left
only in the commit history.

The replacement check drops the next-byte heuristic entirely and instead
tiles the whole offset-sorted entry list against `orig/g.exe`: for each
adjacent pair of entries `(a, b)`, `a`'s computed end (`a + 1 + len_byte`)
must not exceed `b` (no overlap — a real cut/overrun would overlap), and
if the gap between them is under 40 bytes, that gap must contain no
"alphanumeric" byte (a genuine truncation would strand a partial word
there; a length byte alone is one byte, not a run).

**Measured result, independently verified against the numbers relayed for
this task (they matched exactly):**

```
749 entries, 748 adjacent pairs
0 overlaps
633 exact abutments (end == next start)
115 gaps (end < next start)
  69 gaps >= 40 bytes  -- inter-region separators
  46 gaps <  40 bytes
      7 clean (no alphanumeric byte)
     39 contain an alphanumeric byte -- the check's assertion fails on the
        first of these it reaches (offset 0x23A0)
```

The 69 large gaps (210 to 17,285 bytes) sit at the boundaries between
separate string regions of the binary — e.g. between the splash-screen
box-art block and the main dialogue block, or between the last recovered
string and the executable's end — not inside any string's payload. They
are inter-region padding/other-data spans, not stranded text.
