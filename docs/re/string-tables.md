# Indexed string array tables (Task 4c)

Source: `data/string_tables.json`, generated by
`tools/extract_tables_indexed.py` (pure Python, reads `orig/g.exe` directly —
no Ghidra step needed once the table bases were located).

## Why this exists

Task 4b recovers strings the code addresses by a literal 16-bit pointer
operand. It structurally cannot recover strings the code reaches by *index
arithmetic* — a Pascal `array[0..N] of string[255]` addressed at runtime as
`base + i * 256` (each element occupies a fixed 256-byte slot regardless of
its actual text length, per Borland Pascal's fixed-capacity shortstring
layout). For such an access pattern, only the table's *base* address ever
needs to appear as a literal operand; each element's address is computed at
runtime (base register + index register * 256) and never appears anywhere
in the binary as a static immediate. No scan of instruction operands,
however broad, can recover an address that is never written down as an
operand — this is a structural limitation of pointer-based recovery, not a
gap in Task 4b's extraction breadth.

## How the tables were located

Task 4b's coverage check (`tools/test_string_pointers.py`) compares its 764
recovered pointers against Task 2's 657 non-suspect blind-scan entries and
found 67 entries neither recovered as a pointer nor covered by a recovered
pointer's payload span. Sorting those 67 by file offset revealed 53 of them
sitting at a strikingly regular stride of `0x100` (256) bytes apart, in two
separate contiguous runs: offsets `0x123de, 0x124de, 0x125de, ...` and
`0x12ef2, 0x12ff2, 0x130f2, ...`. A constant 256-byte gap between successive
short, semantically-related strings (ranks in one run, a graded "crookedness"
ladder in the other) is the signature of a fixed-size shortstring array, so
each run's first offset was taken as a candidate table base and walked
forward at stride 256 to confirm.

## Extraction method

`tools/extract_tables_indexed.py` walks `off = base + i * stride` for
`i = 0, 1, 2, ...`, starting from each table's base offset. For each `i` it
reads the length-prefixed CP866 shortstring at `off` (length byte `blob[off]`,
followed by that many payload bytes) using the same content filter as Task
4b: a well-formed entry requires length in `1..200` and every payload byte to
be printable ASCII (`0x20..0x7E`), CP866 high-range (`0x80..0xF1`), or one of
the separator bytes `0x07`/`0x0A`/`0x0D`. The walk stops at the first `i`
that fails this check — the entry count is **not** hardcoded; it falls out
of the walk. `text` retains the original's `^0`-`^7` colour-markup escapes;
`plain` has them stripped (same convention as `tools/extract_strings.py`).

Both tables happen to be immediately followed by a slot that fails the
content filter (a short-length or non-printable-byte record used for
something else at runtime, e.g. table padding or a following unrelated
structure), which is what naturally terminates each walk at the correct
count.

## Why pointer recovery (Task 4b) cannot find these

Both tables sit far from `CODE_0`'s segment base — well beyond the reach of
a single 16-bit near-immediate relative to any code segment actually used in
this binary (see `docs/re/string-pointers.md`, "Known limitation"). More
fundamentally, even if reachability weren't an issue: a runtime index
computation (`base + i*256`, `i` coming from a variable — the character's
current rank, level, etc.) is, by construction, never written down anywhere
as a static instruction operand for any `i` other than possibly `i = 0`.
Task 4b's extraction considers every instruction's scalar and address
operands and found none landing on any of these 53 element offsets except
possibly the table base itself — confirming this is not a gap in operand
coverage but a fundamentally different addressing mode that literal-operand
scanning cannot see. Task 4b's coverage assertion
(`tools/test_string_pointers.py`) excludes both table's offset ranges for
exactly this reason rather than counting them as pointer-recovery losses.

## Consumers

Task 2b merges `data/string_tables.json`'s entries into `data/strings.json`.
Tasks 9b and 10 read the two tables by name (`"ranks"`, `"krutizna"`) to
render the character's class/rank and крутизна level in the ported game.
